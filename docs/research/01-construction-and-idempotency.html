Building icons that can vary

How to construct icons so one source can become a variable font with Material Symbols' four axes, and how to make every weight and size correction come out the same every time you run it.

Repo: snds/variance. Everything below the bench was measured with a small working prototype in that repo, unless it says otherwise.

The short answer. Draw the skeleton, not the outline.

Each icon should be stored as centre-lines plus a few rules (stroke alignment, caps, joins, which parts knock out). Every master is then generated from that one source by a fixed recipe.

Done that way, masters match point-for-point by construction, and rebuilding gives a byte-identical font. Exporting outlined art from Figma or Illustrator cannot promise either.

What we're matching

Google's own guide gives the axes and their jobs. It does not publish how the font was built, how many masters it has, or which axis corners are drawn by hand.

AxisRangeDefaultWhat it does
FILL0 – 10Outline to solid. Meant for state changes, such as a selected tab.
wght100 – 700400Stroke weight. The guide notes it can also change the overall size a little.
GRAD−50 – 2000Finer thickness control with almost no size change. Use about −25 for light icons on dark backgrounds, or to match a text face's grade.
opsz20 – 4824Optical size. Stroke thickness shifts with rendered size so the icon looks the same at 20 px and 48 px.

Source: Material Symbols guide. Some third-party pages list GRAD as −25 to 200; Google's guide says −50.

The five things every master must share

A variable font stores one shape and a set of moves for each point. That only works if each master has the same points in the same order. If any of these differ, the shape twists or explodes between masters.

  1. Same number of contours, in the same order.
  2. Same number of points in each contour.
  3. Same point types: a corner stays a corner, a curve handle stays a handle.
  4. Same start point on each contour.
  5. Same direction on each contour: clockwise stays clockwise.

One more rule follows from these. Never delete points to change a shape; collapse them. When FILL goes to 1, the hole in a ring doesn't disappear. Its four points shrink onto the centre.

Why exported outlines break

The usual route is "Outline stroke" in Figma or Illustrator at each weight. Those tools use a general stroker. It adds or drops points depending on the stroke width, because that is the right call for a single drawing.

The prototype measured this with Skia's stroker, the same engine family behind Chrome and many design tools:

Check mark (round join)121414same in all

The check mark loses two points at the thin weight, so the masters can't interpolate. The ring matches, but carries more than three times the points it needs, and nothing guarantees those points line up across weights. Either way, someone has to repair it by hand, per icon, per master. That is the step this project should remove.

The construction method

Store skeletons and rules

An icon source is a set of parts. Each part is one of three kinds:

PartDrawn asStroke ruleWhy
Closed strokeClosed centre-line pathGrows inward. Butt caps don't apply.The silhouette stays put as weight changes, so icons keep their footprint on the grid.
Open strokeOpen centre-line pathCentred. Butt caps, round joins.A round join is one curve at every width, so the point count never changes. Miter joins jump between shapes at sharp angles.
SolidFilled shapeOffset by a fraction of the stroke change.Dots and small solid marks still need to gain weight with the rest.

In Figma or Illustrator this is just an un-outlined stroked drawing, exported as SVG with strokes intact. Designers keep working the way they already do. The pipeline reads the stroke paths as skeletons and never asks for outlined art.

Mark knockouts by direction

A filled check circle shows the check as a hole in a solid disc. An outlined one shows the check as ink inside an empty ring. These look like opposite constructions, but one rule covers both.

Fonts use the nonzero fill rule. If the check is wound the opposite way to the outer ring, it reads as ink inside the empty counter at FILL 0, and as a hole in the solid disc at FILL 1. No point is added, removed or reversed. The source only needs to tag the part as a knockout.

Make every correction a recipe

Each axis is a small, fixed table or formula that turns the source into a master. The prototype uses these. The numbers are placeholder choices, not Material's values, which are not published.

CorrectionRecipe in the prototype
WeightStroke width from a table: 100 → 0.67 px, 400 → 2 px, 700 → 3.33 px, straight lines between.
Optical sizeMultiplies the stroke: ×1.10 at 20, ×1.00 at 24, ×0.85 at 48. Small icons get relatively heavier strokes so they survive the pixel grid.
GradeAdds to the stroke: −0.2 px at −50, +0.67 px at 200. The silhouette doesn't move.
FillRing counters collapse to their centre. Knockouts are handled by direction.
ClearanceAs a ring thickens inward, inner details scale about their own centre to keep the same share of free space they have at 400. Capped between 0.5× and 1.1×.

Making it idempotent

Idempotent means re-running the pipeline on the same source always gives the same result, and running a cleanup step twice changes nothing the second time. Four habits get you there.

  1. Always start from the source. Every master is computed from the skeleton. A correction is never applied on top of an earlier output, so errors can't pile up.
  2. Topology comes from the source, not the geometry. Start points, direction and contour order are set by the part list. If the pipeline picked "the top-left point" in each master instead, a tie could pick different points at different weights.
  3. Round once, at the end. Coordinates stay exact until the last step, then snap to whole font units. Curves are converted to the font's quadratic format jointly across all masters (fontTools cu2qu), so each master gets the same number of curve pieces.
  4. Pin everything that isn't design. Font files carry created and modified dates. Unless they are fixed, every build differs even when nothing changed.

Corners need their own masters

The font only stores one move per axis, then adds them together. That's exact when corrections are straight lines. Clearance and fill aren't, so the corners drift from what the recipe would draw.

CornerDrift at 24 px
wght 700 · opsz 200.23 px
wght 100 · opsz 48 · GRAD −500.80 px
wght 700 · opsz 20 · GRAD 2000.82 px
wght 700 · FILL 11.32 px

The fix stays automatic. The pipeline measures drift at every corner, and adds a corner master only where drift passes a budget, such as a quarter pixel. Because the recipe is fixed, the same corners get added every time.

Proposed pipeline

  1. Ingest. Accept SVG from Figma, Illustrator or anywhere. Turn shapes into paths and apply transforms, the way Google's picosvg cleans SVGs for color fonts.
  2. Classify. Sort each path into closed stroke, open stroke, solid or knockout. Read tags from layer names, with sensible guesses when they're missing.
  3. Lint the construction. Flag what the recipes can't handle, such as outlined strokes, miter joins, or a detail too close to a ring. Explain the fix in design terms.
  4. Generate masters. Run the recipes for every master location.
  5. Compatibility gate. Exact checks must pass. Heuristic checks are listed for review, not treated as failures.
  6. Corner pass. Measure drift and add corner masters over budget.
  7. Compile. Build the variable font with fontTools, with private-use code points and name ligatures.
  8. Proof. Produce a proof sheet like the one above, plus a file hash to show nothing changed when nothing should have.

Decisions for you

  1. Source format. I recommend stroked skeleton SVGs as the only input for v1. The other path is to accept outlined art and fit a skeleton to it automatically. That's much harder and loses detail.
  2. Hand-drawn overrides. Should a designer be able to supply a hand-drawn master for one icon at one location, such as opsz 20? Material seems to need this for small sizes, where detail has to go, not just thicken.
  3. First axes. I'd ship wght and FILL first, then opsz and GRAD. Those two cover most product needs, and FILL holds the hardest open problem.
  4. FILL midpoints. Options: an extra master at 0.5, a remapped FILL curve so the awkward middle passes quickly, or designing counters to shrink around details. I'd test all three on ten real icons before choosing.
